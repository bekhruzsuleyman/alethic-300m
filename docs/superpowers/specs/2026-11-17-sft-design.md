# Alethic-Code-Small SFT design (2026-11-17)

Status: APPROVED by Bekhruz on 2026-11-17 ("I approve"). The items under "Still undecided" stay open; the plan treats each as a switch, not a blocker.
Last update: 2026-11-17 evening, section "Update: decisions from the dataset work" added at the end. Where it disagrees with the text above, the update wins once approved.

## Intent
Turn the finished base model (alethic-300m, GQA, 302,908,416 params, seq_len 4096, tokenizer alethic-tokenizer-v1) into a model that answers real questions in English, Uzbek and code. Style: serious, short, good answers, less talk, more work. Long code must be possible, so the model learns to manage its own context.

## Goals
- Instant answers by default.
- Thinking: answer may start with <thinking>, or open it in the middle. Max 3 blocks, 300 thinking tokens total, harness forces the close.
- Map skill: model writes a section map (name + end line), and the harness retrieves sections from the file it holds.
- <map> as an action the model can call anywhere: the harness saves full history to disk, replaces the old big chunk with the map, keeps the user's own messages word for word. Harness forces a compaction at 75% of the window (3,072 tokens).
- Modes: Normal (plain answers) and Max (map + retrieval). Ultracode (run code, fix from the error) is reserved for later.

## Non-goals / anti-goals
- No training on text written by Claude or by any model whose terms forbid it.
- No long chatty answers. No guessing of names: names are copied from the numbered code.
- Not a v1 goal: Ultracode, model-decided mode routing line.

## Constraints
- The model was trained at 4,096 tokens: answers up to about 3,500 tokens including the question.
- Read budget per pass about 3,000 tokens (about 200 numbered lines).
- Control tokens: <sp00>..<sp63> (ids 4-67) are available; thinking uses <sp11>/<sp12>.
- Bekhruz writes the gold examples (about 600, 50 held out as the test set). Rest generated by DeepSeek (see My calls / Decisions) and filtered by the checker.

## Approaches considered
1. Plain SFT only (fast baseline, no context skills).
2. Plain SFT + thinking + map skills, harness holds the full file (chosen).
3. Notes with remembered signatures (rejected: small models forget exact names).
Chosen: 2, because names are copied from code that was just read.

## Decisions (as decided by Bekhruz)
- Thinking starts with <thinking> when the topic needs it; it may also appear in the middle.
- Map = section names with end lines, e.g. "game mechanics 100l -> render loop 300l". (Superseded by the v1 format below: `name start-end`.)
- Model may call <map> anywhere; the old big chunk is deleted from the window.

## My calls (not yet approved)
- Harness numbers lines (L101 ...), snaps end lines to function boundaries with ast, shifts later end lines after edits.
- Sections at most about 100 lines; bigger ones are split into sub-sections.
- v1 map labels are real function/class names; meaning-level group names later.
- Plan line in code answers: one line.
- Mix: about 2,500 instant, 1,000 thinking-at-start, 500 thinking-in-middle, 1,000 map examples (about 2.8M tokens, about 1 minute of SFT compute for 3 epochs).
- Generator: DeepSeek (Bekhruz's choice, 2026-11-17). Its Terms of Use (updated 2026-03-27) allow training other models; AI-generated output must be labelled if the dataset is published. Bekhruz creates the account and API key himself; the key stays in a local file and is never shown to Claude. Test 20 Uzbek questions first; Bekhruz judges the quality. Every generated example gets source: deepseek in its header. If open weights are used instead of the API, read that model's LICENSE first.
- Map training pairs can come from real git diffs (functions changed by a commit = functions the task needed) in permissively licensed repos.

## Left to the builder
Style guide, one-page writing tool (token counter toward 1M, source field per example, live checks), checker, SFT training mode, held-out test, harness (numbering, ast snapping, compaction).

## Tests
- Held-out 50 gold examples, graded by Bekhruz.
- Map: continuation runs from map + section vs full file (pass rate).
- Thinking: loop check, forced-close rate.

## Update: decisions from the dataset work (2026-11-17, all PROPOSED until approved)

### Tools v1
calc, list, read, write, edit, shell(command). `shell` replaced `run(file)` today (27 calls converted in batches 1-2). `search` (Wikipedia + Wiktionary) is tool 7: UNDECIDED. Rule if adopted: tool list has `search` -> the model searches; no `search` -> it says "I am not sure". Live data (weather, prices) stays "not sure". Mixed-language examples must show a tool list without `search`.

### Map while reading (agreed in chat, now written down)
- Read in chunks of about 100 lines (first chunk 80-110). After each chunk the model writes `<map>`.
- Format: `name start-end`; a function still open at the chunk end is `name start-`. Functions and classes only (my call).
- After the map, the old chunk result is replaced by the stub `<result> (dropped; see map) </result>`. The next read range comes from the map.
- Test: share of map `end` lines that equal the `ast` end line. Starting bar 70%.

### Loss mask
Loss on: assistant text, plan, calls, write/edit content, map. No loss on: user, every `<result>`, stubs, carried goal/todo/done. Failed assistant attempts are masked, and so is any step the assistant chose to fail on purpose (planned fails in skeletons 0605, 0613, 0631, 0640 and session stage 4). A bug that lives in the file or the tool result is not the assistant's mistake. Wrong attempts come from a real `shell()` run (about 10% error-retry slice).

### Example types
T multi-turn chats; E idea evaluation (paired pushbacks: no new fact -> assistant holds; a real new fact -> assistant updates; verdict first, 80 words or fewer, no flattery); W long project sessions in windows; X terminal; S search; M mixed Uzbek/English; Z prompt injection (about 15, proposed). `mix` is a new language value.

### Windows and context management
A session is cut into windows that each fit 4,096 tokens. Every window after the first starts with harness-written `<goal>`, `<todo>`, `<done>` (no loss). The first real session (Practice Mistake Logger) is 6 windows; the build prototype turns it into 8 samples (window 5 splits at map events).

### Skeleton pipeline
DeepSeek writes only structure (FILES, USER, PLAN, STEP lines with EXPECT, FINAL). A script runs every command for real in a sandbox and records the output, so results are never invented. 38 hand-invented results in batches D/E/H and 48 rebuild examples are to be regenerated this way.

### Harness requirements found
Fixed working directory name; `LC_ALL=C`; `git init -q -b main`; `git log --format=%s` only; commits with `-c user.name=t -c user.email=t@t.t`; no hashes or timestamps in output; accent-insensitive EXPECT for search; exact-title lookup for empty cases; `uz.wikipedia.org` for Uzbek questions; full Wiktionary page for translation tables; a `write` content line starting with `<call>` is a converter edge case.

### Security (proposed)
- Sandbox is the hard wall: non-root, no secrets, about 10 s per command (60 s for installs), 256 MB, 100 KB output. Builds run on Modal, not on Bekhruz's laptop.
- Network allowed only to an allowlist: pypi.org, files.pythonhosted.org, registry.npmjs.org, github.com, en.wikipedia.org, uz.wikipedia.org. Installs are pinned, inside a project venv.
- Harness command policy blocks sudo, curl, wget, ssh, pipes into sh, absolute paths, `..`, symlink escape; `rm -rf` only after confirmation. Confirmation rule (proposal): deletes and history rewrites only.
- Second layer in data: refusal examples and type Z (injection inside file and tool results).
- Evaluation: 50 unsafe prompts with at least 95% refusal; harness blocks 100%; 20 injection cases obeyed 0.

### Go/no-go per 50 held-out examples
Tool-call parse at least 98%; no-call accuracy at least 90%; map continuation at least 70%; pilot checker pass at least 85%.

### Dataset state today
About 219 usable examples (4.4% of the 5,000 plan): batches 1-2 (200, with 146 usable after fixes, 48 to rebuild, 6 to remove), controls 0301-0343, mixed 0501-0530. Search skeletons (30) and terminal skeletons (45) exist but need the real run. Dataset rating by me: 5/10.

### Still undecided (needs Bekhruz)
`search` tool; rule v8 (plan or thinking, never both); Uzbek apostrophe (`'` vs `oʻ`); `source` naming; sandbox technology (proposal: Modal containers); confirmation rule; approval of this doc.

## Update 2: search and the error fallback (2026-11-17 evening, rewritten after the first copy was lost)

- `search` is in v1 (decided in chat). Tools v1: calc, list, read, write, edit, shell, search.
- Search-on-error rule (approved in chat): run, see the error, read the failing code once. If the fix is visible, fix it directly (no search). If not, search the error text (at most 2 searches) and apply the fix. If both give nothing useful, do not invent a fix: say "I am not sure", say what was tried, give one next step.
- Search results are untrusted text. Type Z (prompt injection) covers injection inside files, search results and pasted text. The network allowlist grows per source (docs.python.org first).
- Type F: 50 skeletons (0701-0750: 30 search_fix, 8 search_empty, 12 self_fix), all checked by `tools/fcheck.py` on Python 3.13. Builders still need `search` steps (real fetch, EXPECT_IN_RESULT, NONE plus UNIQUE for search_empty) and `read`/`edit` steps in the terminal builder.
- Prompts written for T/E (0801-0880, multi-turn and paired idea evaluation) and Z (0901-0916).
- Multi-agent (a parent writes a short brief, a child runs in its own 4,096 window and returns a short result) comes after the single-agent pilot passes go/no-go. Not v1.

## Update 3: deep thinking (Max mode) (2026-11-17, PROPOSED until approved)

Decided in chat: thinking budget "1,200 tokens recommended, even more if needed", and "it even can map inside thinking".

- Budget: Max mode soft limit 1,200 thinking tokens, hard cap 2,000 (harness forces the close). Longer reasoning only through a thinking map. The old rule (3 blocks, 300 tokens) stays for the default mode.
- Thinking map: inside `<thinking>` the model may write `<map> known: ... | open: ... </map>`. The harness then replaces the earlier thinking text with the stub `<thinking> (dropped; see map) </thinking>` and keeps the map, the same way a read result is dropped after its map. Training samples are cut into windows at the map.
- Domains: math, code, design, multi-language projects, and mixes of these.
- Source rules: no thinking text written by Claude. Problems, verifiers and request prompts are mine; the thinking is written by DeepSeek's thinking mode (k attempts per problem, run by Bekhruz's own script and key; re-read the terms for that mode before the first run). A trace is kept only if its final answer passes a verifier, shortest verified attempt first.
- Problems: math from own generators checked with sympy; code from real fixes in permissively licensed repos (MIT, Apache-2.0, BSD) with their tests as the judge; multi-language mini projects (Python+C, Python+Node, Go+Python, Rust+Python, C+Makefile) that must build and pass a hidden test; design problems with checkable numbers (at most 15%, weakest verifier).
- Quality over quantity: about 200 verified traces (math 60, code 60, multi-language 50, design 30). Bekhruz reads 20 random survivors before training. Held-out: 30 problems per domain, never seen by the thinking model.
- Go/no-go: thinking accuracy at least 15 points above instant on held-out verified problems; loop rate at most 2%; forced-close rate at most 10%.
- Plan: `docs/superpowers/plans/2026-11-17-sft-deep-thinking.md` (9 tasks).
- Open: terms of DeepSeek's thinking mode; sandbox toolchains (gcc, rustc, go, node) on Modal; whether the hard cap should be above 2,000 once the window logic exists.
